Reading of the table (each claim same-session / same-harness):
- The decode+memory upset SURVIVES: LiteRT beats every loadable arm on decode and beats the
  non-mmap arms on memory by 6-9.5x.
- QUALITY goes to MLX-OptiQ: 91.0% — +6 pts over the wNa8o8 LiteRT ships, at 0.66x its
  decode speed. Nearest-quality framing: LiteRT 85.0 vs MLX-PTQ 84.0 -> LiteRT is 1.14x
  faster at matched quality with 6x less memory.
- The PTQ->QAT quality gap re-measured with stored reports: 84.0 -> 91.0 (+7 pts; the old
  "78 -> 87, 9 pts" claim came from the defective harness era — supersede it).
- llama.cpp: google/gemma-4-E2B-it-qat-q4_0-gguf aborts in llama_vocab::impl::load —
  "load: empty token at index 237922" then GGML_ASSERT(id_to_token.size()==token_to_id.size()).
  Reproduced: on-device vendored b8999, macOS brew 8680, macOS latest release b10064
  (2026-07-17). unsloth Q4_K_M (PTQ) loads fine => defect is in this file's conversion.
  The official-QAT row therefore reads "unloadable" — that is the measurement. Its usable
  fallback (Q4_K_M) is also the QUALITY floor of the table at 76.0%.
- On-device quality-task answers (sanity only): litert 9/9 correct; both MLX quants ~8/9;
  llama Q4_K_M quality-task output came back EMPTY on device (needs a look — its Mac-side
  GSM8K ran fine, so likely a stop-token/template quirk in the app path).
- core-ai row — the "EngineFactory wall" was a MISDIAGNOSIS (root-caused + fixed 2026-07-18,
  commit 21404c6). Three real causes, none of them the engine path:
    1. our own warmup(queryLength: 8) after createEngine — S=1-only graph => binary-layer
       NDArrayDescriptor fatal that `try?` cannot catch (this WAS the whole "wall"; the
       community-bench 07-14 note misattributed the same crash to EngineFactory);
    2. gemma-4 ships its chat template as a separate chat_template.jinja, which
       swift-transformers does not read => raw-encode prompt => degenerate "<turn|>" output;
       fixed by inlining a minimal template into the bundle's tokenizer_config.json
       (canonical bundle under leaderboard/models/ patched too; the HF-published
       mlboydaisuke/gemma-4-E2B-CoreAI copy still needs the same fix);
    3. COREAI_CHUNK_THRESHOLD=1 set at app init (gated to gemma4 core-ai launches).
  GemmaPLEDeviceBench itself uses the SAME official EngineFactory + engine.generate — the
  "low-level PreparedModel runner" description was wrong. So the row's provenance is: Apple's
  standard engine path + two local additions (staticInputBuffers patch, own export).
